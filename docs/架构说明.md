# 漫画翻译助手 — 架构说明与规划

## 一、当前架构

```
┌──────────────────┐   ┌──────────────────────────────────────────────┐
│ 漫画翻译助手.exe   │   │            translate.py（核心流程）             │
│ (app.py 统一GUI)  │──▶│  输入识别→解压→MITS翻译→重打包→弹窗/序号输出      │
│ 侧边栏三页面:      │   └───────┬──────────────────────────┬────────────┘
│ 快速翻译/工作台/服务│           │ 子进程                     │ 钩子注入
│ SakuraManager    │   ┌────────▼────────┐      ┌───────────▼──────────┐
│ theme 亮/暗主题   │   │ manga-image-    │      │ 自定义模块             │
└──────┬───────────┘   │ translator      │      │ sfx_filter.py        │
       │ 子进程         │ (MITS 引擎)     │      │ name_translation.py   │
       ├─► translate.py │                  │      └───────────────────────┘
       ├─► re_render.py └────┬────────────┘
       └─► sakura_server.py   │ HTTP (OpenAI 格式)
          (pythonw, 日志) ┌───▼────────────┐
                          │ sakura_server.py │  ── llama-cpp-python
                          │ (127.0.0.1:8080)│  ── sakura-7B 模型(6GB,GPU)
                          └─────────────────┘
```

**默认数据流**: 输入 → 解压/收集 → MITS 检测文字 → OCR(mocr) → sakura 翻译 → 拟声词处理 → 人名音译 → 擦字(lama) → 嵌字渲染 → 输出

**无窗口列级 OCR 流**（`background_ocr.py`，当前 OCR 改造主线）:

```text
原图 -> CTD 文本框+掩膜 || 独立子进程 PP-OCRv6 整页检测/识别
    -> 框交叉验证/Paddle 独有框补漏 -> 多列拆分/去重 -> 每列三次 MangaOCR
    -> 双模型文字仲裁 -> 不确定框人工核对队列 -> 阅读顺序 -> 句级翻译单元+列级嵌字坐标
```

该入口批量运行时不启动窗口、不控制鼠标键盘，并强制从本地缓存加载 MangaOCR 与
PP-OCRv6。PaddleOCR 放在 `paddle_venv` 隔离子进程，避免 PaddlePaddle 与主环境的
Torch/Transformers 冲突；目录批量只初始化一次 Paddle。输出同时保存列级 `columns` 和句级
`translation_units`：完整句用于翻译，组成句子的
原列框用于擦字和嵌字，每个排版框允许总宽高 10% 的余量。Windows“照片”清单只作为可选
基准，按框 F1 ≥ 90%、字符错误率 ≤ 10%、多字符正文零遗漏三项验收。

**Windows“照片”OCR 自动流**（`photos_translate.py`）:

```text
原图 -> Windows 照片/扫描文本 -> 逐列文字+蓝色选区坐标 -> N/N 完整性校验
    -> 面板排序/句末合句 -> Sakura -> 气泡擦字或白描边覆盖 -> 输出
```

该路径的文字和坐标均来自照片 `OcrControl`，不会调用 MangaOCR。`photos_capture.py`
检测照片生成的白描边文字岛，逐列点击复制，并把显示坐标映射回原图；
`photos_translate.py` 保留这些列坐标完成翻译和嵌字。

**Windows“照片”辅助订正流**（`photos_capture.py batch` + `background_ocr.py`）:

```text
短暂前台采集 base/overlay/全选清单
    -> ORB + RANSAC 映射到原图坐标（误差门禁）
    -> 后台 CTD / PP-OCRv6 / MangaOCR + Photos 候选融合
    -> schema 2 人工核对（恢复/新增/拒绝/改框/容器/断句）
    -> 兼容 schema 4 OCR JSON
```

该流不把 Photos 框直接交给擦字器。Photos 提供第三候选和完整性证据，最终框必须覆盖原图正文
墨迹。`panel_index + container_id` 是句子分组硬边界。`ocr_review.py apply-patch` 支持哈希绑定的
可维护核对补丁；恢复的忽略候选保留在 `restored_ignored_regions` 审计中。

**统一界面架构**（2026-08-02 新增）:
- `app.py`: 主应用，左侧 220px 侧边栏（导航×4 + 服务胶囊 + 主题切换）+ 右侧 QStackedWidget 四页面
- 页面1 快速翻译（gui.py 的 TranslatePage）、页面2 调整工作台（workbench.py 的 WorkbenchPage）、

- `service_manager.py`: sakura 生命周期（pythonw 子进程启动、QTimer 3s 轮询 /health、仅终止自己启动的进程）
- `theme.py`: 亮/暗双主题 QSS 设计系统（teal 主色 #14b8a6、卡片 16px 圆角、渐变按钮），选择持久化 config/ui.json

## 二、可扩展点（钩子位置）

MITS 管线中注入的 5 个钩子（`manga_translator.py`）：

| 钩子 | 时机 | 用途 |
|---|---|---|
| `page_skip_hook` | translate() 最开头（模型加载前） | 译文缓存命中→返回缓存成品图，跳过整条管线 |
| `pre_translate_hook` | OCR合并后、翻译前 | 拟声词过滤（气泡判定/数量阈值）；术语表 pre_dict 亦在此阶段 |
| `transliteration_hook` | 翻译后、过滤前 | 无法翻译的片假名→先查翻译记忆，未命中再音译 |
| `post_translate_hook` | 翻译后、擦字前 | 记忆修正→拟声词词典修正→记忆自动记录 |
| `mid_pipeline_hook` | 渲染后 | 导出调整状态（擦字图+文本框JSON）+ 写入译文缓存 |

渲染定制（`rendering/`）：字号三步算法（最小字号22→框≤110%→最多加一列）、竖排默认**右→左**（`vertical_rtl` 可切左→右）、重嵌字框内裁切居中。

## 四、OCR 里程碑与新项目边界（2026-08-04）

OCR 主线已经冻结为 schema 4 数据生产器。后续“逐块擦字、整句翻译、精准嵌字”放到独立
项目实现，当前仓库只负责稳定地产出原图坐标系中的列框、阅读顺序和翻译单元。

```text
当前项目（OCR producer）                    新项目（render consumer）
background_ocr.py                           schema 4 loader
  -> columns / manual_review_queue             -> review gate
  -> reading_order                              -> per-column masks
  -> translation_units                        -> sentence translation
  -> layout_bbox_10pct                         -> inpaint + constrained layout
  -> benchmark                                 -> final image + state + QA
```

边界原则：翻译按 `translation_units` 整句进行，擦字按 `layout_regions` 逐列进行。排版先使用
`layout_bbox_10pct` 软边界；只有记录并复核的回退可从完整框直接计算 20%，20% 是绝对上限。完整字段契约、样本清单、下游验收条件见 `OCR_交接文档.md`；可直接用于新
项目的提示词见 `NEXT_PROJECT_PROMPT.md`。

人工核对默认开启：双模型文字不一致、单模型定位、弱框重叠、低重复一致性或 Paddle 文字
接管会产生 `pending` 队列并阻断翻译。`--no-manual-review` 是显式绕过开关；绕过时仍保存
候选和原因，避免把风险隐藏在最终译图中。人工决定由 `ocr_review.py` 校验并回填。

当前四页样本 1/8/19/22 共保留 70 列。1/8/19 页相对 Windows“照片”的框 F1 分别为
97.14%、100%、98.25%，CER 分别为 5.48%、4.55%、1.48%，多字符正文漏列均为 0。

## 五、未来程序规划

**问题**: 检测器对 小字/艺术字/复杂背景文字 会漏检，导致原文未翻译。
**方案方向**（可组合）:
